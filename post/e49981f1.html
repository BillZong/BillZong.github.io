秘钥安全管理设计方案

2025-10-10

目标

  • 预付卡整个系统中，依赖多个关键性第三方业务服务，并需要保存关键的 APIKey，但在生产环境部署时，开发、运维均有可能会接触到这些关键信息。
  • 所以，我们需要设计一整套的业务流程来防止关键信息泄露，防止内部人员获取或破坏这些关键信息，对业务造成不可挽回的影响。

词汇表

  • Key Management Service (KMS)
    • 一种基于云的加密和密钥管理服务，可以轻松创建和控制加密密钥，以加密跨 AWS 服务和应用程序中的数据 。 它使用 FIPS 140-3 验证的硬件安全模块 （HSM） 来保护密钥，并通过 AWS CloudTrail 提供详细的审计日志记录，从而集中控制密钥管理、权限和使用情况。
    • 关键特性：创建低风险存储的秘钥、AWS 存储中间件原生集成、高安全级别且丰富的秘钥管理、审计合规、即时告警等。
  • SecretManager (SM)
    • AWS 提供的私密信息存储系统。可帮助我们在整个生命周期内管理、检索和轮换数据库凭证、应用程序凭证、OAuth 令牌、API 密钥和其他密钥。许多 AWS 服务都已在 Secrets Manager 中存储和使用密钥。

系统设计

  • Broker 收敛敏感配置的访问，并使用业务客户端特有的 KMS Key 来获取敏感数据。
  • Config Manager 需要定期访问并刷新 SM 的业务版本，确保分钟级的热加载，实现业务 APIKey 的自动轮转。
  • KeyManager 使用离线工具加密对应的重要配置项，并将加密后的内容和加密用公钥提供给 Operator 配置。Operator 无法通过任何软件工程学的方式解密这些配置项。
  • KeyManager、Operator 的任何修改，都会触发审计，并发布告警到对应的业务响应群。
  • 开发调试时，需要避免访问 SM 以及 KMS，要求配置管理能支持开发模式的配置加载。

风险点及方案

  • 开发轮转更新工具
    • Lamda + 限制授信 IAM
    • MVP 阶段暂不考虑秘钥轮转。
  • 数据库秘钥配置
    • 可考虑定期轮转更新，但会造成更高的运维和审计成本。
    • MVP 阶段暂时先不考虑更高级别的安全策略。
  • 运维人员错误配置
    • SM 有完整的审计功能和 Hook，可通过告警及时发现错误情况，并实现快速回滚。
    • 明确不可使用的业务配置应停止应用并及时告警。
    • MVP 阶段暂不考虑该业务功能。
  • 核心管理人员错误配置
    • 方案同上。
  • KeyManager 更换人员
    • 即时更新 IAM 权限，并提供审计告警。
    • MVP 阶段暂不考虑该业务功能。

遗留问题

  • 第三方服务后台审计监管
    • 需要介入第三方的审计，确保即时监控到所有变更（创建、更新、删除等）。
    • 必须有备用账号，且明确所有状况的响应方案。
    • MVP 阶段暂不考虑该业务功能。
