AI-Native 现代分析系统的底层重构

第六章: AI-Native 现代分析系统的底层重构

The Underlying Restructure for AI-Native Modern Analytics

引言：当智能体成为分析系统的执行主体

在前五篇的技术演进中，企业分析系统完成了一系列关键的架构跃迁：从经典数据仓库集中管理业务数据，到分布式计算与云原生数仓突破算力瓶颈；从独立语义层统一指标口径，到大模型借助 Semantic IR 理解自然语言意图；再到上一章引入的业务对象图（Ontology），将业务对象、对象关系与可执行动作统一到面向操作的语义抽象层中。

然而，能够理解业务意图、查询数据并触发业务动作，并不意味着系统已经具备生产级自主运行的能力。当分析任务从单轮问答扩展到多步骤推理、跨系统数据检索、动态代码执行和高风险业务操作时，系统面临的问题发生了根本性变化：大模型如何分工协作？不同数据源与工具如何统一接入？昂贵的推理算力如何合理分配？敏感数据如何在模型执行过程中得到保护？当智能体开始拥有实际操作能力后，企业又如何对其行为实施统一授权与审计？

这些问题无法仅靠更大的模型或更复杂的 Prompt 解决。它们要求分析系统从"以模型为中心的应用编排"，进一步演进为以职责分离、确定性执行、统一协议和全局治理为基础的 AI-Native 系统架构。

本篇讨论的 AI-Native，并不是在传统 BI 系统上简单增加一个聊天窗口，也不是把所有业务逻辑交给一个自主智能体[1][2]

，而是将智能体、模型、数据平台、执行环境与治理机制作为一套完整的工程系统进行重新设计。

一、复杂分析任务下的多智能体职责分离架构

1. 从单一全能模型到分工协作的工程范式

在早期的 AI BI 实践中，最直观的实现方式是将用户问题、数据库 Schema、指标定义以及工具说明一并交给一个大语言模型，再要求它完成从问题理解到 SQL 生成、结果解释的全部工作。

这种方式在简单场景下具有较低的开发成本，但随着业务复杂度上升，单一模型的职责开始出现明显冲突。

首先，上下文复杂度持续增长。一个跨销售、财务和供应链的分析任务，可能同时涉及数百张表、数千个指标、多个业务系统的 API 以及不同的权限规则。将所有信息直接注入同一上下文，不仅增加 Token 消耗，还会使真正相关的信息被大量无关内容淹没。

其次，不同任务对模型能力的要求并不相同。意图分类强调低延迟和稳定性，复杂根因分析需要多步推理，SQL 执行依赖确定性的数据库引擎，而结果审计则要求独立验证计算口径与业务约束。让同一个模型承担所有工作，容易导致职责边界模糊，也难以针对不同环节独立优化成本与可靠性。

最后，错误容易在长链路中传播。如果模型在最初阶段误解了“净收入”的定义，后续即使成功生成 SQL、完成统计计算并生成流畅的解释，整个分析过程仍然可能得出错误结论。自然语言表达的可信度并不能替代计算过程的正确性。

因此，生产级架构应从单一模型调用转向职责分离的多智能体协作网络[2:1]

（Multi-Agent Analytics Network）。这里的核心不是简单增加 Agent 数量，而是将原本混合在单个模型中的任务，拆分为具有明确输入、输出、权限与验收条件的工程组件。

2. 四类核心角色及其职责边界

在企业分析场景中，可以将复杂任务拆分为 Router、Retriever、Executor 与 Auditor 四类核心角色。

Router：意图解析与任务规划。 Router 负责理解用户问题，识别分析目标、约束条件和预期输出，并将复杂任务拆解为可执行的子任务。例如，面对“分析本季度利润率下降的原因，并评估是否需要调整采购计划”，Router 不应直接生成一段 SQL，而应首先识别利润率分析、历史趋势比较、成本因素拆解以及采购调整评估等子任务，并确定它们之间的依赖关系。

Retriever：业务语义与数据上下文检索。 Retriever 负责从语义层、指标目录、数据血缘系统、业务对象图及相关元数据中，获取当前任务真正需要的信息。它不仅要找到相关表和字段，还需要识别指标定义、数据时效性、可用的 Join 路径以及当前用户可访问的数据范围。通过将上下文检索独立出来，系统可以避免每次请求都把完整 Schema 与业务知识发送给大模型。

Executor：受控查询与计算执行。 Executor 将经过确认的分析计划转换为实际执行任务，包括调用语义层 API、提交 SQL、运行受限的 Python 分析代码，或者读取经过授权的业务对象。它的关键职责不是自由发挥，而是在明确的工具权限、资源配额和执行边界内完成计算。对于 SQL，系统应通过确定性编译、静态校验和数据库权限控制约束执行过程；对于动态代码，则应使用隔离的沙箱环境限制文件、网络、进程和资源访问。

Auditor：独立校验与结果审计。 Auditor 负责验证分析结果是否符合既定口径、约束条件和数据质量要求。例如，利润率是否使用了正确的收入与成本定义，聚合前后的统计粒度是否一致，样本量是否足以支持结论，以及执行过程中是否出现了权限违规或数据缺失。对于重要结果，Auditor 可以要求执行独立查询、检查计算不变量，或者对关键汇总指标进行交叉验证。

需要强调的是，这四类角色是逻辑职责，不一定对应四个独立运行的大模型。对于高频、低复杂度任务，它们可以由同一个服务中的不同模块实现；只有当任务复杂度、隔离要求或吞吐需求足够高时，才有必要将其拆分为独立 Agent 服务。职责分离的目的，是明确系统边界，而不是追求 Agent 数量。

3. 多智能体协作的运行时架构

从工程实现看，多智能体系统不能依赖各个模型之间自由传递自然语言来维持协作。否则，一个角色对业务概念的模糊理解可能被下游角色不断放大，最终难以确定错误发生在哪个阶段。

更可靠的方式是建立结构化的任务契约（Task Contract），规定每个角色接收什么输入、产生什么输出，以及在什么条件下允许任务继续执行。

例如，Router 输出任务计划，Retriever 输出带有来源标识的语义上下文，Executor 输出查询结果与执行元数据，Auditor 则输出明确的校验结论。各阶段通过结构化数据交换，而不是依赖隐含在长篇自然语言中的约定。

用户问题 │ ▼ Router / Planner 意图解析、任务拆解、风险初判 │ ▼ Retriever 语义定义、元数据、对象与权限上下文 │ ▼ 结构化任务计划与执行约束 │ ▼ Executor 语义 API / SQL / Python Sandbox / Actions │ ▼ Auditor 口径校验、结果复核、策略合规检查 │ ├── 校验失败 ──► 限定范围内重试或请求人工介入 │ ▼ 结果解释与授权后的业务动作

在这一流程中，任务状态、重试次数、超时和错误处理均应由运行时编排器控制。模型可以提出下一步行动，但不应自行决定是否绕过权限检查、无限重试或突破资源限制。

例如，当 SQL 执行失败时，系统可以把经过脱敏的错误信息返回给 Executor，允许其在限定次数内修正查询；当检索到的指标定义存在冲突时，系统则应暂停自动推理，要求业务负责人确认口径，而不是让模型任意选择一个定义。

这种架构将概率性的模型行为限制在明确的工程契约之内，使复杂任务具备更好的可调试性、可恢复性与可验证性。

4. 独立校验不等于绝对正确

多智能体架构并不会天然消除幻觉。如果 Auditor 与 Executor 使用相同的错误指标定义、相同的上下文，甚至由同一个模型简单重复生成答案，那么所谓的“双重校验”可能只是重复同一种错误。

因此，关键结果应尽可能通过不同证据来源进行验证：使用独立 SQL 复算汇总指标、对照语义层中的权威定义、检查数据血缘与更新时间，或者验证总量与分组汇总之间的数学关系。

对于无法通过确定性规则验证的业务判断，系统应明确区分事实、推断与建议，并保留不确定性，而不是将模型生成的解释包装成已被证实的结论。

多智能体架构的真正价值，不是让模型之间互相证明对方正确，而是将任务分解、执行、校验与授权变成可独立检查的工程环节。

二、互操作性协议标准化：Model Context Protocol（MCP）

1. 从定制化工具集成到统一协议

当智能体开始承担跨系统分析任务时，另一个突出问题随之出现：工具集成的复杂度迅速上升。

一个企业分析系统可能需要访问数据仓库、指标服务、数据目录、Python 沙箱、业务对象图和外部业务 API。传统做法通常是为每种工具单独开发调用适配器，并在应用层维护各自的参数格式、认证方式、错误处理和返回结构。

随着工具数量与模型应用数量增加，这种点对点集成方式会产生明显的维护成本。工具的接口变化可能影响多个 Agent，权限校验容易散落在不同适配器中，开发团队也难以统一管理工具发现、参数校验和调用日志。

Model Context Protocol（MCP）为这一问题提供了一种开放的协议化思路[1:1]

。MCP 的定位并不是专属 BI 的查询协议，也不是新的数据库执行引擎，而是为大模型应用与外部数据源、工具及上下文提供统一的交互约定。

它试图解决的是：不同的 AI 应用如何以一致的方式发现和调用外部能力，而不必为每种模型与工具组合重复构建专用集成。

2. MCP 的核心架构与协议原语

在 MCP 的典型架构中，Host 是承载 AI 交互与任务编排的应用；Client 负责在协议层面与 MCP Server 建立连接；Server 则向客户端暴露其管理的数据、工具和上下文能力。

MCP 的核心交互能力通常通过三类原语表达。

Resources（资源）：用于向模型应用提供可读取的上下文，例如指标定义、数据字典、经过授权的元数据、业务规则文档或分析任务相关的数据快照。Resources 主要解决上下文如何被发现和读取的问题。

Tools（工具）：用于暴露可以被调用的操作，例如查询指标、执行受限 SQL、启动统计分析、检索业务对象或提交业务操作请求。工具通常具有明确的名称、参数 Schema 和返回结构。

Prompts（提示模板）：用于提供可复用的任务模板或交互流程，例如标准化的异常分析流程、财务指标解释模板或数据质量排查步骤。

这些原语承担不同职责：Resources 提供上下文，Tools 提供可执行能力，Prompts 则帮助应用组织任务交互。它们不是权限系统的替代品，也不意味着任何被暴露的工具都可以不经授权地执行。

从协议传输层看，MCP 使用 JSON-RPC 作为消息交互基础，并支持通过标准输入输出等方式进行本地进程通信，也支持基于 HTTP 的远程通信模式。具体传输方式、认证机制与能力支持应以所采用的 MCP 规范版本和实现为准。

3. MCP 在 BI 系统中的工程映射

在现代分析系统中，MCP 可以成为 Agent 访问企业数据能力的一层标准化协议入口。

例如，企业可以将语义层的指标查询服务包装为 query_metric 工具，将数据目录包装为 search_metadata 工具，将受限的分析环境包装为 run_analysis 工具，并将 Ontology 中允许调用的业务动作包装为经过授权的操作接口。

此时，Agent 不必了解每个下游系统内部使用何种编程语言、数据库方言或服务框架，而是通过工具描述与参数契约发现并调用相应能力。

需要注意，MCP 并不会自动把任意数据库变成语义一致的数据平台。它可以标准化工具接入方式，却不能替代指标口径治理、SQL 编译器、数据访问控制或事务一致性机制。一个定义错误的 query_metric 工具，即使完全符合 MCP 协议，依然可能返回错误的业务结果。

因此，合理的架构应将 MCP 放在工具互操作层，而将业务语义与确定性执行能力保留在相应的服务层中。

### 4. 标准化接口不等于标准化信任

协议统一后，企业仍然需要解决一个关键问题：工具是否值得信任，以及它可以在什么条件下被调用。

工具描述可能来自内部服务，也可能来自第三方服务器。即使工具的参数 Schema 合法，也不能据此认定它的行为安全。工具调用可能读取超出任务需要的数据、访问不可信的外部资源，或者执行具有副作用的操作。

因此，MCP 的生产级部署需要配合服务身份认证、工具白名单、参数校验、超时控制、调用配额和执行结果审计。对于会修改数据或触发业务动作的工具，还应在工具本身与下游服务中实施权限检查，而不是只依赖模型是否“理解了安全要求”。

MCP 的工程价值在于降低异构工具集成的摩擦，而不是消除系统边界[1:2]

。开放协议解决互操作性，确定性策略解决授权问题，底层业务系统则继续承担最终执行责任。

三、混合模型路由与隐私计算边界

1. 从统一大模型到分层模型路由

多智能体系统投入生产后，模型成本将成为一个无法回避的工程问题。

如果每一个请求都交由能力最强、推理成本最高的大模型处理，系统虽然可以获得较强的复杂问题处理能力，却会在大量简单任务上浪费算力。例如，识别用户想查询哪个指标、提取时间范围、判断是否需要调用某个工具等任务，通常不需要与跨域根因分析相同的推理预算。

反过来，如果为了节省成本而将所有任务交给小模型，又可能导致复杂问题拆解能力不足、长链路规划失败，最终通过更多重试消耗掉原本节省的资源。

因此，AI-Native 分析系统需要引入模型路由（Model Routing）机制，根据任务复杂度、准确性要求、数据敏感等级、响应时间和预算等条件，将不同请求分配给适当的执行路径。

这不是简单地按照模型参数规模划分任务，而是建立一种面向任务特征的分层决策机制。

2. 专用小模型、推理模型与确定性引擎的协同

一种可行的混合架构包含三个核心部分。

第一层：专用小模型（Specialized Small Model）。 对于高频、结构明确的任务，可以使用成本较低、延迟较小的模型完成意图分类、字段抽取、常见语义映射和工具路由。这些任务往往具有相对稳定的输入输出结构，可以通过标准化数据集、约束解码与回归测试持续优化。对于规则高度确定的步骤，直接使用传统分类器或规则引擎也可能比调用语言模型更加可靠。

第二层：推理模型（Reasoning Model）。 当任务涉及多个业务域、复杂因果分析、长链路规划或多轮证据整合时，系统再调用具有更强推理能力的模型。例如，在利润率下降的分析中，系统可能需要联合分析价格变化、产品结构、供应链成本和客户流失等多个因素，并判断哪些因素能够得到数据支持。

第三层：确定性执行引擎（Deterministic Engine）。 无论前面的模型如何理解问题，涉及指标计算、权限判断、SQL 执行和事务提交的关键步骤，都应尽可能交由具备明确契约的确定性组件处理。模型负责提出结构化意图，执行引擎负责检查其合法性并完成实际计算。

三者共同构成一种混合计算范式：

用户请求 │ ▼ 轻量模型 / 规则路由 │ ├── 简单任务 ──► 专用小模型或确定性规则 │ └── 复杂任务 ──► 推理模型与多步任务规划 │ ▼ 结构化语义请求 │ ▼ 确定性编译与权限校验 │ ▼ SQL / 分析代码 / 工具 │ ▼ 结果校验与审计

该架构将模型推理与业务计算的职责明确分开：模型负责概率性的意图理解和问题拆解，确定性引擎负责在既定约束下执行计算与操作。模型路由则根据任务需要，动态决定何时值得投入更高的推理成本。

3. 模型路由的关键不是价格，而是总成本

在实际系统中，模型的单位 Token 价格并不能直接代表整个任务的真实成本。

如果小模型生成的任务计划频繁出错，导致多次 SQL 重试、额外的上下文检索和人工复核，那么较低的单次调用价格并不一定带来更低的总成本。反之，某些复杂问题使用能力更强的模型一次完成规划，可能减少整体执行次数与端到端延迟。

因此，模型路由应关注端到端总拥有成本（TCO），综合评估模型调用成本、上下文构建成本、工具执行成本、失败重试成本和人工介入成本。

同时，模型选择不能只依赖成本。对于高风险财务分析、敏感数据访问和可触发业务操作的任务，路由策略还应纳入数据敏感级别、允许的数据处理位置、模型能力验证结果及审计要求。

工程上可以为不同任务定义明确的路由策略。例如，简单指标查询走轻量路径；涉及多域关联和复杂解释的问题进入推理路径；高风险 Action 则必须经过确定性授权和人工审批，无论使用何种模型都不能绕过这一约束。

此外，路由系统应建立持续评测机制，监控不同模型在实际业务任务上的成功率、幻觉率、平均延迟、单位成功任务成本与人工介入率。只有在这些指标可比较的情况下，模型路由才能从经验性的模型选择演进为可优化的基础设施能力。

4. 可信执行环境（TEE）与数据隐私屏障

模型路由解决的是计算资源如何分配的问题，但在金融、医疗、供应链和企业内部经营分析等场景中，数据隐私还构成另一条独立的架构约束。

传统的访问控制可以决定用户是否有权读取某份数据，却不一定能够回答：当敏感数据进入模型推理服务、动态代码执行环境或第三方工具时，运行时的数据暴露风险如何控制？

可信执行环境（Trusted Execution Environment，TEE）为这一问题提供了一种硬件辅助的安全机制[3][4]

。TEE 通过处理器支持的隔离技术，在特定威胁模型下保护受保护执行环境中的代码与数据，降低其被宿主操作系统、虚拟机管理层或其他不可信软件直接读取或篡改的风险。

结合远程证明（Remote Attestation）机制，调用方可以验证特定执行环境的身份及其测量状态，并据此决定是否释放相应的密钥或敏感数据。密钥管理系统可以进一步将数据解密权限与经过验证的执行环境、工作负载身份和策略条件绑定。

在 AI-Native 分析系统中，这类机制可以应用于敏感数据的受控解密、部分模型推理、受保护的代码执行或密钥使用流程。例如，系统可以要求只有通过指定远程证明策略的分析工作负载，才能获得解密某类敏感数据所需的短期密钥。

但必须明确，TEE 并不是数据隐私的万能解决方案[3:1]

。它无法自动消除模型输出中的敏感信息泄露，也不能保证运行代码本身没有逻辑漏洞。侧信道攻击、实现缺陷、密钥配置错误和受保护环境之外的数据流动，仍然可能构成风险。

因此，TEE 应与数据最小化、传输加密、静态脱敏、输出过滤、网络访问限制和严格的密钥生命周期管理共同使用。对于不允许敏感数据离开指定边界的场景，系统还必须审查模型供应商的处理位置、日志保留策略与实际的数据流，而不能仅凭“使用了 TEE”就宣称满足全部合规要求。

隐私保护的核心不是让所有计算都进入硬件安全区，而是明确哪些数据可以在哪里被谁以什么方式处理，并通过可验证的机制落实这些边界。

四、治理面（Governance Plane）与全链路可观测性

1. 从数据访问控制到智能体行为治理

在传统 BI 系统中，治理体系的核心任务相对明确：通过身份认证、角色权限、行级安全（RLS）、列级权限和数据脱敏，决定用户能够查看哪些数据。

当分析系统从只读查询扩展到 Agentic BI 后，治理对象开始发生变化。智能体不仅能够读取数据，还可能执行 Python 代码、调用外部 API、修改业务对象状态，甚至触发采购申请、排产调整或客户运营流程。

因此，企业需要进一步回答：谁可以让 Agent 调用哪些工具？哪些数据可以进入模型上下文？哪些查询允许被执行？哪些业务对象可以被修改？哪些操作必须等待人工批准？

这些问题已经超出传统数据权限管理的范围，需要在数据权限之上建立面向智能体运行过程的统一治理面。

Governance Plane 并不是一个独立产品名称所能概括的单一模块[5]

，而是一组跨越身份、策略、执行与审计的控制能力。它应当能够在任务规划、上下文检索、工具调用、查询执行和业务动作等阶段实施一致的约束。

2. 治理面应覆盖哪些控制边界

首先是身份与权限上下文的连续传递。系统必须区分发起请求的用户、执行任务的 Agent、实际调用工具的服务身份以及最终访问数据的主体。Agent 不能因为拥有一个高权限服务账号，就自动获得所有用户数据的访问能力。系统应根据用户身份、任务目的、资源范围与当前策略确定有效权限，并将必要的授权上下文传递给下游执行组件。

其次是工具与执行环境的能力约束。不同角色应当只获得完成任务所必需的工具权限。Retriever 可以读取经过授权的元数据，但不应默认拥有修改业务对象的能力；Executor 可以提交受限查询，却不应自动获得任意网络访问或任意文件系统写权限。对于动态代码执行，沙箱需要限制 CPU、内存、执行时间、文件系统与网络访问，并防止任务通过间接路径突破隔离边界。

第三是查询与业务动作的策略控制。对于数据查询，治理面应结合数据分类、行列权限、查询复杂度、结果集规模与敏感字段规则进行检查。对于具有副作用的 Action，则应在执行前验证对象权限、操作类型、参数范围和业务状态约束。涉及高额采购、财务审批或关键生产配置的操作，还应通过确定性策略判断是否需要人工确认。

第四是策略执行的可追溯性。系统不仅要记录某个请求是否被允许，还应记录与决策相关的策略版本、授权主体、资源范围、审批状态及执行结果。发生问题时，企业需要能够重建当时的决策依据，而不只是看到一条“调用成功”的日志。

3. Human-in-the-loop：将人工审批固化为确定性控制

上一章已经讨论过 Human-in-the-loop（人在回路），即当 Agent 准备执行敏感或高风险业务动作时，由人工确认后再继续。

在生产系统中，这种机制不能仅通过 Prompt 提醒模型“重要操作请询问用户”。提示词属于概率性约束，无法保证模型每次都遵守。

更可靠的实现方式是由策略引擎判断操作风险，并在执行层设置不可绕过的审批状态机[5:1]

。例如，Agent 可以生成一份采购申请草案，但实际提交动作必须经过授权服务检查；如果策略要求审批，系统就创建待审批任务，并拒绝在审批完成之前调用最终提交接口。

这一流程需要处理的不仅是审批按钮，还包括审批人的身份验证、申请参数与批准内容的一致性、审批有效期、重复提交和状态变化等问题。

例如，某项采购申请经过审批后，如果金额、供应商或商品数量发生变化，系统就不应继续沿用原有审批结果，而应根据策略重新判定是否需要审批。这可以防止 Agent 在获得一次授权后，通过修改参数将操作扩展到原本未获批准的范围。

对于不可逆或影响范围较大的操作，还应采用幂等键、操作状态检查、审计记录和必要的补偿机制。人工审批控制的是业务授权，而执行系统仍然需要保证操作过程具有可靠的事务语义。

4. 为什么不应依赖宽泛的 Thought Log

当 Agent 执行过程出现问题时，企业通常希望知道系统为什么得出某个结论、调用了哪些工具，以及结果是如何产生的。

一种直观的做法是记录模型生成的完整推理文本。然而，将宽泛的 Thought Log 作为审计基础存在多个问题：自然语言推理文本并不等同于真实执行证据；其内容可能不稳定，无法准确反映底层工具实际执行的操作；记录完整上下文还可能增加敏感信息暴露与存储成本。

生产级系统更需要工程化的执行追踪（Execution Trace），重点记录可以验证的事件与数据流转[6]

。

一条完整的分析链路至少应包含以下关键节点：

这里的重点不是记录所有原始内容，而是建立能够重建执行过程的证据链。对于敏感数据，日志应优先记录稳定标识、哈希、脱敏摘要与必要的元数据，而不是默认保存完整的原始数据集、凭证或模型上下文。

同时，执行追踪应使用统一的 Request ID、Trace ID 和跨服务关联标识，将 Agent 编排服务、MCP Server、语义层、查询引擎与业务动作服务连接起来。只有这样，运维人员才能在一次跨系统任务中定位具体的延迟来源、失败环节和权限决策。

5. 从可观测性到可审计的运行闭环

Agentic BI 的可观测性不应只关注传统服务的 CPU、内存和请求延迟，还需要增加与模型及业务执行有关的指标。

在成本维度，应统计各模型的调用量、Token 消耗、任务级成本和重试开销；在性能维度，应记录端到端延迟、工具调用耗时、数据库执行时间与排队时间；在质量维度，应追踪任务完成率、SQL 执行成功率、校验失败率、人工介入率和结果引用完整性；在治理维度，则应监控权限拒绝、审批等待、策略冲突和高风险操作的实际执行情况。

这些指标必须与具体任务和策略版本关联，才能用于定位问题。例如，某次分析耗时明显上升，可能不是模型推理变慢，而是 Retriever 返回了过多上下文、Executor 执行了低效查询，或者 Auditor 因校验失败触发了额外重试。

与此同时，系统还需要建立明确的日志保留、访问控制和审计查询机制。审计数据本身可能包含敏感信息，因此日志平台也必须接受权限治理、脱敏和访问审计，不能成为绕过原有数据访问控制的第二条通道。

最终，Governance Plane 与 Execution Trace 应形成互补关系[5:2][6:1]

：前者定义系统允许做什么，后者记录系统实际做了什么。通过将授权策略与执行证据结合起来，企业才能把 Agent 的自主执行能力纳入可验证、可追责的工程边界之内。

五、AI-Native 现代分析系统的参考架构

前述技术并不是彼此独立的功能模块，而是共同构成一套完整的分析运行时。

在数据底座之上，Lakehouse 或数据仓库负责持久化存储与大规模计算；语义层统一指标定义、业务规则与数据访问契约；Ontology 将数据集映射为具有业务含义的对象、关系与可执行动作。它们共同为上层智能体提供相对稳定的业务语义与确定性执行接口。

在交互与编排层，Router、Retriever、Executor 和 Auditor 根据任务契约完成分工协作[2:2]

。MCP 可以作为连接外部资源与工具的一种标准化协议，而模型路由机制则根据任务复杂度、成本和安全要求，决定使用何种模型或确定性组件。

在安全与治理层，身份认证、策略引擎、工具授权、沙箱隔离、人工审批和执行追踪贯穿整个任务生命周期。TEE 等硬件辅助安全技术可以在特定场景下加强运行时数据保护，但仍需与密钥管理、数据最小化及输出治理共同使用。

这一参考架构不要求所有企业一次性部署全部组件。对于简单的自然语言指标查询，可以先建立语义层、结构化请求和确定性 SQL 执行链路；当任务开始跨越多个数据域时，再引入独立检索与任务规划；当系统需要访问大量异构工具时，可以通过 MCP 减少集成成本；当模型调用规模增长或敏感数据约束变得严格时，再进一步建设模型路由、受保护执行环境与统一治理面。

这种渐进式建设路径比一开始就构建复杂的多 Agent 网络更符合工程实际。架构的价值应通过可衡量的业务结果体现，而不是通过组件数量体现。

第六章核心技术主张

AI-Native 现代分析系统的关键，不是让一个大模型承担越来越多的职责，而是将智能能力嵌入一套具有明确边界的工程系统。

多智能体职责分离解决复杂任务的分解、执行与校验问题；MCP 降低模型应用与异构工具之间的集成成本；混合模型路由在任务质量、响应延迟和算力成本之间建立可优化的平衡；TEE 与其他隐私保护措施帮助系统控制敏感数据的运行时暴露风险；Governance Plane 和 Execution Trace 则使智能体的查询、工具调用与业务动作能够接受统一授权和事后审计。

这些技术共同指向一个重要的架构原则：

模型可以负责理解意图、提出计划与生成候选方案，但系统必须负责约束权限、执行计算、验证结果并记录证据。自主性越强，确定性的执行边界与治理机制就越重要。

企业真正需要的不是一个能够自由行动、却无法解释其执行路径的智能体，而是一套能够在明确约束下自主完成任务，并在必要时暂停、回滚、升级给人工处理的分析基础设施。
