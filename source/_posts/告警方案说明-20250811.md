## 告警消息协议

AlertManager消息协议-V1
```json
{
    "status": "firing", // resolved 目前会被忽略
    "groupLabels": {
        "fingerprint": "告警的组指纹" // 可选。如果设置 alert.labels.use_group_fingerprint = "true"，则会使用组的finger_print作为告警dedup_key
    },
    "alerts": [{
        "status": "firing", // resolved 目前会被忽略
        "labels": {
            "response_team": "swap:backend", // 必须。服务响应团队名，告警服务会以此命名。接入需要找运维团队注册。告警必须带上相应的标签。否则，会转到Default服务中（有可能被忽略）
            "dedup_key": "swap:backend:api-crash:20250813", // 可选。如果设置了，则会使用该字段作为 dedup_key
            "use_group_fingerprint": "true", // 可选。如果没有设置dedup_key，并设置了该字段，则使用 groupLabels.fingerprint 作为 dedup_key，否则会使用 fingerprint 作为 dedup_key
            "project": "proj01", // 可选
            "application": "app01", // 可选
            "environment": "release" // 可选
        },
        "annotations": {
            "summary": "告警标题" // 可选
        },
        "startsAt": "开始时间", // 可选
        "endsAt": "结束时间", // 可选
        "generatorURL": "告警的反向链接", // 可选
        "fingerprint": "告警的label指纹" // 可选
    }]
}
```

参考 PagerDuty 的 PD-CEF 模板
https://developer.pagerduty.com/docs/send-alert-event#example-request-payloads

WebHook消息模板 -V1
```json
{
  "response_team": "swap:backend" // 必须。服务响应团队名，告警服务会以此命名。接入需要找运维团队注册。告警必须带上相应的标签。否则，会转到Default服务中（有可能被忽略）
  "dedup_key": "swap:backend:api-crash:20250813", // 可选。业务告警的唯一ID，不同ID会视为不同告警，不填会认为每次都是不同的告警，慎重填入。
  "title": "告警标题", // 可选。告警标题
  "project": "proj01", // 可选。
  "application": "app01", // 可选。
  "environment": "release", // 可选。debug, test, stage, release
  "source": "monitoringtool:cloudvendor:central-region-dc-01:852559987:cluster/api-stats-prod-003", // 可选。具体标记由运维完成，或者AlertManager的generatorURL
  "severity": "warning", // 可选，不填默认为 warning。 warning -> P3, error -> P2, critical -> P1
  "urgency": "low", // 可选。告警紧急性。不填，则会根据 severity 自动生成 (warning -> low, error -> high, critical -> high)
  ... // 其余业务告警字段和内容可自行组织，但不要和已有的字段冲突
}
```


## 组织策略说明

* 优先级配置和说明

  * 管理员创建团队后，默认会有5个级别，严重性从高到低分别为 P1-P5，只有管理员有权限进行相关配置。

  * 优先级 ID 在接口调用时可不填入，配置服务时可提供默认优先级。但在需要手动升级告警或明确高优先级告警时，应填入对应的优先级ID。

  * 优先级 ID 可以通过接口查看

  * ```bash
    curl -X GET \
      -H 'Authorization: Token token=你的API_KEY' \
      -H 'Accept: application/vnd.pagerduty+json;version=2' \
      'https://api.pagerduty.com/priorities'
    ```

  * 返回结果为

  * ```json
    {
      "priorities": [
        {
          "id": "PLABC123", // 这个就是需要使用的优先级ID
          "name": "P1",
          "description": "", // 全局配置后生效
          "self": "https://<your-subdomain>.pagerduty.com/priorities/PLABC123" // 对应的页面上也可以找到其ID
        },
        ...
      ]
    }
    ```

* 按业务线拆分不同的 Service

  * 一个 Service 只对应一个主责团队，避免多人模糊响应。
  * 每个主责团队负责人必须留电话，以避免告警升级后通知不及时。

* 告警应按严重性分流

  * P1（致命故障） → 直接打电话 / App 推送 → 一级值班 → 立即升级
    * 立即电话通知，10 分钟内响应
  * P2（重大功能异常） → 常规值班 → 超时升级到二级值班
    * 值班表内 30 分钟响应
  * P3（非紧急） → 仅 邮件提醒，不打扰值班
    * 工作日内处理

* 设置默认兜底策略

  - 建立一个“平台级响应“的兜底升级策略，防止告警“掉地上”无人响应
  - 如果告警匹配不到任何业务的策略 → 自动丢到兜底值班组

* P1 告警升级链要尽量短（<30 分钟到管理层）
  * 暂定最多3个层级的告警升级链。值班人 -> 主责团队负责人 -> 管理层
