## BPE算法

### BPE概念与核心原理

* 概念：BPE 最初是一种数据压缩算法，后来被引入自然语言处理（NLP）领域。它的核心思想是：**从字符级（或字节级）开始，迭代地将最常出现的字符对（或词素对）合并为一个新的子词，直到达到预设的词表大小（Vocabulary Size）。**

* 核心工作原理：
    - **初始化**：将训练语料拆分为单个字符（或字节），并在每个单词末尾添加结束符（如 `</w>`），统计所有字符的频次。此时，基础词表只包含单个字符。
    - **统计频次**：统计语料中相邻字符对（Pair）的出现频次。
    - **合并最高频对**：找出频次最高的一对（例如 `e` 和 `s` 组合成 `es`），将它们合并为一个新的子词，并加入词表。
    - **循环迭代**：重复上述“统计-合并”步骤，直到**词表达到指定大小**（如 32,000 或 50,257）或**最高频次低于阈值**。
    - **推理分词（Tokenization）**：当新文本输入时，分词器会按照训练时记录的**合并规则顺序**，由粗到细地将文本拆分为词表已有的最大子词。

### BPE推荐的Golang库

在 Go 语言生态中，实现或兼容主流大模型 BPE 分词的优秀开源库包括：

- **[tiktoken-go/tiktoken](https://github.com/pkoukk/tiktoken-go)**
  - **特点**：纯 Go 实现的 OpenAI `tiktoken` 库的高性能克隆版本。
  - **适用场景**：完全兼容 GPT-3.5、GPT-4 等模型的 `cl100k_base` 或 `o200k_base` 编码，适合开发 OpenAI 相关的应用、Prompt 长度计算及 RAG 系统。
- **[daulet/tokenizers](https://github.com/daulet/tokenizers)**
  - **特点**：对 Hugging Face 官方 Rust 版本 `tokenizers` 的 Go 语言绑定（通过 CGO）。
  - **适用场景**：需要加载 LLaMA、BERT、CLIP 等主流开源模型的 `tokenizer.json` 文件。性能极高，但依赖 CGO 交叉编译稍显复杂。
- **[sugarme/tokenizer](https://github.com/sugarme/tokenizer)**
  - **特点**：纯 Go 实现的 Hugging Face tokenizers 替代品。
  - **适用场景**：不想使用 CGO，且需要对标准 BPE、WordPiece 算法进行微调或本地训练的场景。

### BPE在Embedding阶段的作用

在深度学习模型（如 Transformer）中，文本无法直接输入网络，必须经过 BPE 分词和 Embedding 两个阶段的衔接：

```text
原始文本 ➔ [ BPE Tokenizer ] ➔ Token IDs (整数) ➔ [ Embedding Lookup Table ] ➔ 稠密向量 (Float)
```

1. **映射离散符号到索引（Token IDs）**：BPE 将文本切割为子词后，将每个子词转换为词表中唯一的整数索引（ID）。Embedding 层正是利用这些 ID 作为**查找表的索引**（Lookup Table）。
2. **彻底解决 OOV（Out-of-Vocabulary，词表外）问题**：传统的全词分词（Word-level）遇到未见过的词会映射为 `[UNK]`，丢失语义。BPE 的基础词表包含所有单字符/字节，任何罕见词或生僻词（如 `Hyperthyroidism`）都会被拆解为已知子词（如 `Hyper` + `thyroid` + `ism`），确保**任何文本都能被映射到 Embedding 向量**。
3. **计算效率与语义表征的平衡**：
   - 如果用字符级 Embedding：序列过长，模型注意力机制（Attention）计算量爆炸，且单个字符缺乏语义。
   - 如果用全词级 Embedding：词表巨大（几百万），导致 Embedding 矩阵极度稀疏，占用海量显存。
   - **BPE 的作用**：用较小的词表（如 5W 左右）实现了高压缩率，缩短了输入 Embedding 的序列长度，提升了计算效率，同时保留了前缀、后缀等形态学语义。

### BPE常见坑点

1. 字节级 BPE（BBPE）中的无效 UTF-8 截断坑

   - **坑点**：现代 BPE（如 GPT 采用的 Byte-level BPE）直接对底层字节（0-255）进行合并。如果文本在不恰当的位置被截断（例如在 RAG 分块、日志截断或滑动窗口中），一个多字节的中文字符（如 UTF-8 占 3 字节）可能被切成两半，产生**非法的 UTF-8 序列**。这会导致 Embedding 阶段查找出错误的 Token ID，产生乱码或模型幻觉。

   - **避坑指南**：在进行文本切片（Chunking）时，**必须先在字符串（Rune/字符）层面进行切分**，确保边界完整，再送入 Tokenizer；或者使用专门支持安全字节解码的 Tokenizer 库，在拼接回文本时使用 `strings.ToValidUTF8` 进行清洗。


2. 空格与特殊字符流失（Whitespace Artifacts）

   - **坑点**：BPE 算法高度依赖空格作为边界处理（例如 GPT 会将空格视为 Token 的一部分，如 ` Ġword`）。如果在前处理阶段误删了连续空格、换行符（`\n`）或制表符（`\t`），会导致分词结果大相径庭，进而导致 Embedding 向量偏离原始语意。
   
   
      - **避坑指南**：严格保持原始输入文本的干净与完整。在文本清洗阶段，**不要盲目使用 `strings.ReplaceAll(text, " ", "")` 剔除所有空格**，必须与模型训练时的预处理（Pre-tokenization）规则保持绝对一致。
   
3. 词表不匹配导致 Embedding 错乱

   - **坑点**：不同模型（如 LLaMA-3、GPT-4、Gemma）的 BPE 词表和合并规则完全不同。误用 A 模型的 Tokenizer 转出的 ID 传给 B 模型的 Embedding 层，系统不会报错（因为 ID 范围可能重叠），但**输出的向量语义会完全风马牛不相及**。

   - **避坑指南**：实行严格的**“分词器-模型一对一绑定”**。在 Go 架构设计中，将 Tokenizer 实例与 Embedding Model 配置封装在同一个结构体中，禁止跨模型复用分词组件。


4. OOVs 降级拆分导致的“长序列性能劣化”

   - **坑点**：当遇到大量专业术语、代码、特殊符号或小众语言时，BPE 无法匹配大颗粒子词，会退化将它们拆解为大量的“单字符”或“单字节”。这会导致经 BPE 转换后的 Token IDs 序列**长度激增**。由于 Transformer 的 Attention 复杂度是长度的平方（O(N²)），这会导致 Embedding 后的计算耗时飙升，甚至超过模型的 Max Context Length 限制。

   - **避坑指南**：在将 Token IDs 传入后续模型前，**必须在 Go 代码中检查序列长度**（如 `len(tokens)`），若超出阈值需提前截断或报警。针对特定垂直领域（如医疗、法律、特定编程语言），应选用专门在该语料上二次预训练、扩充过词表的 BPE Tokenizer。


## WordPiece 算法
WordPiece 是一种自底向上的子词分词算法。它在合并子词时引入了统计学评估，通过最大化语言模型**似然度**来确保合并后的子词最具信息量。
### WP概念与核心原理

* 概念：WordPiece 最初由谷歌用于语音处理，后被广泛应用于 BERT 等双向 Transformer 模型。它在 BPE 的频次统计基础之上，引入了条件概率，专门解决 BPE 盲目合并高频词导致无效子词膨胀的问题。
* 核心原理：
  * 初始化：将所有基本字符和符号放入词表。在非单词开头的子词前添加特殊前缀（如 BERT 中的 `##`）。
  * 互信息评估：不再只看子词 A 和子词 B 的组合频次 $count(AB)$，而是计算合并后的互信息分数： $\text{Score} = \frac{count(AB)}{count(A) \times count(B)}$ 。
  * 合并与迭代：这个分数衡量的是“A 和 B 共同出现的概率是否远大于它们各自独立出现的概率”。算法每次只合并分数最高（最分不开）的字符对，直到词表达到预设大小。
  * 推理（最大前向匹配）：分词时，对整个单词从左到右贪心匹配词表中能找到的最长子词。若匹配到单词内部，则加上 ## 前缀。
### WP推荐的Golang库

* [daulet/tokenizers](https://github.com/daulet/tokenizers)：调用 Hugging Face 官方 Rust tokenizers 的 CGO 绑定库。它是目前支持 WordPiece（尤其是 BERT 的 vocab.txt）性能最高、最纯正的 Go 语言通道。
* [sugarme/tokenizer](https://github.com/sugarme/tokenizer)：纯 Go 实现。它内置了 WordPiece 模型组件，适合在需要完全摆脱 CGO 交叉编译依赖的环境下操作。

### WP在Embedding阶段的作用

* 形态学特征的语义对齐：通过 ## 前缀，WordPiece 在 Embedding 查找表中将“词根”与“词缀”分离开。例如，embeddings 被切分为 embed + ##ding + ##s。在 Embedding Lookup 时，##ding 和 ##s 的向量能代表动名词和复数的普适特征，显著降低了 Embedding 矩阵对变形词的存储压力。
* 确定性的索引映射：与 BPE 类似，每个子词拥有固定的词表 ID，能够直接作为 Embedding 的位置索引，将离散符号转化为连续的稠密向量。

### WP常见坑点

* 前缀在数据清洗中的“丢失坑”
   * 坑点：WordPiece 极度依赖 ## 标记来区分子词在单词中的位置（如 un 和 ##un 是完全不同的向量）。在一些做 RAG 或文本后处理的 Go 代码中，研发人员不小心通过正则表达式误删或误改了 ##，会导致整句话在 Embedding 查找时全部错位。
   * 避坑指南：任何对 Token 数组或分词文本的过滤逻辑，必须将 ## 作为合法字符保留。在转回原始文本时，使用 strings.ReplaceAll(text, " ##", "") 还原空格，而不是直接暴力消除。

* 生僻词退化为大量的单字符（UNK/字符激增）
   * 坑点：经典的 WordPiece（如 BERT 词表）没有采用 Byte-level。当遇到完全不在基础词表内的生僻汉字、特殊 emoji 或乱码时，它会触发 [UNK]（Unknown）机制，或者强行拆解成极碎的单字符，导致输入 Embedding 的序列长度暴增或语义彻底丢失。
   * 避坑指南：在 Go 管道中，送入 WordPiece 之前先进行 OOV 字符清洗，或使用支持多语言扩展的扩充词表。对超长序列传入 Embedding 层前，务必执行 len(tokens) 截断拦截。


## UnigramLanguageModel算法
Unigram Language Model 是一种基于概率生成模型的自顶向下子词分词算法。它从一个巨大的词表开始，通过不断优化整体语料损失来剔除冗余词。

### ULM概念与核心原理

* 概念：与 BPE/WordPiece 这种“从小变大”的合并逻辑相反，Unigram 是一种“从大变小”的剪枝算法。它将分词问题转化为一个语言模型优化问题，能够为一段文本提供多种分词路径及其概率。
* 核心原理：
  * 初始化大词表：从语料中提取一个极为庞大的初始词表，包含几乎所有的单词、高频短语和单字符。
  * 期望最大化训练（EM 算法）：基于当前的词表概率，计算语料的似然度（Likelihood）。
  * 计算损失（Loss）：对词表中的每个子词进行评估：假设从词表中删掉这个子词，原本由它组成的句子就必须拆成更碎的子词，这会导致整体语料的似然度下降。似然度下降最少的子词，就是“冗余子词”。
  * 剪枝迭代：每次剔除掉贡献最小的 10%~20% 的子词，重新训练，直到词表缩减到目标大小。
  * 推理（Viterbi 算法）：分词时，因为词表中存在多种切分可能，算法利用维特比（Viterbi）算法找出一条概率最大的最佳切分路径。
### ULM推荐的Golang库

* [google/sentencepiece](https://github.com/google/sentencepiece) (Go 命令行或 C 绑定)：Unigram 最权威的实现是谷歌的 SentencePiece。在 Go 中通常通过 CGO 绑定其 C++ 核心，或者在数据管道中将其作为独立的微服务调用。
* [daulet/tokenizers](https://github.com/daulet/tokenizers)：Hugging Face 的 Rust 核心同样完整实现了 Unigram 算法，通过该库可以完美支持像 T5 这类基于 Unigram 的大模型分词。

### ULM在Embedding阶段的作用

* 支持分词正则化（Tokenization Regularization）：这是 Unigram 独有的杀手锏。在 Embedding 训练阶段，它可以依据概率故意输出非最优的次优分词组合。例如，“机器学习”可以 80% 几率切分为 机器/学习，20% 几率切分为 机/器/学/习。这样可以强迫 Embedding 层在训练时接触到不同粒度的数据，极大地增强了 Embedding 向量对文本噪声（如同音字、错别字）的抗干扰能力。
* 无天然空格语言的端到端对齐：配合 SentencePiece，Unigram 将空格转化为特殊符号 _。在 Embedding 检索中，中英文等不同形态的语言都可以共享同一套统一的基础字节表征，无需前置复杂的第三方分词工具。

### ULM常见坑点

1. 确定性推理与 RAG 检索不匹配的“概率坑”

   * 坑点：由于 Unigram 支持概率分词，如果在构建 RAG 向量知识库（Embedding Indexing） 时开启了随机正则化分词，而在用户提问（Query Inference） 时使用了确定性分词，就会导致同一句话转出的 Token ID 序列完全不同，进而导致向量相似度检索（Vector Search）彻底失效。

   * 避坑指南：在数据预处理和推理线上，Go 代码中必须封装两套配置：模型训练/微调阶段允许开启 sample_proba > 0 的随机分词；而线上 Embedding 推理、RAG 向量库构建、Token 计数阶段，必须强制关闭随机性，使用确定的最优路径（Viterbi 极大似然结果）。

2. Viterbi 动态规划解码的“性能坑”
   * 坑点：Unigram 分词由于在推理时需要对一句话的所有潜在切分路径进行动态规划计算，其计算复杂度高于 BPE 简单的哈希查表。在 Go 高并发处理海量文本时，可能会成为 CPU 的性能瓶颈。
   * 避坑指南：在 Go 并发架构中，避免单协程处理超大文本块。充分利用 Go 的 sync.Pool 复用分词器实例，并合理使用 goroutine 将长文本分段并发处理。对于高并发网关，可前置一级 LRU Cache（以原始文本为 Key，以 Token IDs 为 Value）来拦截高频重复文本。
