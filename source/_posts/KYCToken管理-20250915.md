## KYC Token 生命周期与风险对照表

| Token 类型                       | 生命周期                                     | 常见用途                                            | 丢失后的风险                                                 | 安全建议                                                     |
| -------------------------------- | -------------------------------------------- | --------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **临时上传/查询 Token**          | 几分钟 ~ 几小时                              | 用户完成一次性 KYC 表单上传、查询状态               | 被盗用者可能提交/查询一次 KYC，影响有限（通常还需绑定回调域名或 session） | - 不保存在客户端<br />- 仅在后端内存或缓存中使用<br />- 避免写入日志 |
| **会话级 Token**                 | 当次会话有效（比如用户在 30 分钟内完成 KYC） | 用户端嵌入 SDK，完成验证流程                        | 被盗者可伪装成该用户完成流程，但过期后无效                   | - HTTPS 强制传输<br />- 使用 HttpOnly Cookie 或 SDK 自带机制 |
| **长期 API 凭证 / Access Token** | 数天 ~ 数月                                  | 系统对接 KYC 服务商 API，查询用户实名结果、获取报告 | **高风险**：攻击者可批量读取/伪造 KYC 数据，造成数据泄露和合规问题 | - 必须加密存储（KMS、HSM、Vault）<br />- 定期轮换 - 设置调用频率限制 |
| **Refresh Token**（如有）        | 更长（数月）                                 | 用来刷新 Access Token                               | **极高风险**：被盗者可长期获取新 Token，相当于“后门”         | - 绝不可明文存储<br />- 只保存在后端安全存储<br />- 丢失时立即吊销 |

## 结论

- **短期 Token**：可保存，但最好只存在缓存里，过期即失效。
- **长期 Token**：必须加密存储，丢失风险大，要有吊销/轮换机制。
- **绝不要放在客户端或日志**：这是最常见的泄露来源。
