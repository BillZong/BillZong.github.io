在当前的 AI 大模型（LLM）与 AI Agent 工程落地中，业界已经沉淀出了一套专门应对 LLM **非确定性、高延迟、幻觉和上下文限制**的“新一代设计模式”。

以下是经过微软（Autogen/Semantic Kernel）、LangChain、吴恩达（Andrew Ng）以及一线大厂工程验证的 **9 大核心 AI 大模型与 Agent 工程设计模式**。

## AI 大模型与 Agent 工程设计模式全景表

| 设计模式名                                                   | 模式分类                                | 意图 (Intent)                                                | 实现方式与技术栈 (Implementation)                            |
| :----------------------------------------------------------- | :-------------------------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| [**Prompt Chaining** (提示词链模式)](#Prompt Chaining (提示词链模式)) | **工作流模式** (Workflow)               | 将复杂任务拆分为一系列连续的、单一职责的子任务。             | **实现**：利用 LangChain Expression Language (LCEL) 或原生 Python 循环，通过 JSON Schema 传递中间变量。 |
| [**Routing / Classifier** (路由/分类器模式)](#Routing / Classifier (路由/分类器模式)) | **架构/分流模式** (Architecture)        | 根据输入语义，动态将请求分流到不同的下游工作流或模型。       | **实现**：使用 `Semantic Router` 库（基于向量检索）或小模型（如 ModernBERT）输出结构化 Tag 进行 `if-else` 分流。 |

| [**Self-Correction / Reflection** (自我修正/反思模式)](#Self-Correction / Reflection (自我修正/反思模式)) | **质量控制模式** (Quality Control)      | 引入独立的评估环节，让模型检查并纠正自己或他人生成的输出。   | **实现**：在 Prompt 中设计专门的评估人角色（Critique），在工程中设置最大重试上限（如 `max_retries=3`）防止 Token 熔断。 |
| [**Tool Execution Layer** (工具执行层隔离模式)](#Tool Execution Layer (工具执行层隔离模式)) | **安全与控制模式** (Security/Control)   | 将大模型的“工具调用决策”与“工具实际执行”剥离开来，放入沙箱或代码控制层。 | **实现**：使用 Docker 隔离执行环境（如 E2B Sandbox），在 Tool 包装函数中加入硬编码的参数解析验证与安全 ACL（访问控制列表）。 |
| [**Dynamic Memory Management** (动态记忆管理模式)](#Dynamic Memory Management (动态记忆管理模式)) | **上下文控制模式** (Context Control)    | 将历史对话动态划分为短期、长久和实体记忆，按需注入上下文。   | **实现**：结合 Redis 进行短期 Session 缓存，利用 Mem0 或 LangGraph 的 Memory Store 自动提取 “User Profile” 写入图数据库或向量库。 |
| [**Evaluator-Optimizer** (评估-优化器循环模式)](#Evaluator-Optimizer (评估-优化器循环模式)) | **生成迭代模式** (Generation Iteration) | 通过一个专门的评测器提供反馈，驱动优化器不断迭代输出，直至满足客观指标。 | **实现**：例如在 AI 写代码任务中，将 Python 脚本在沙箱运行，抓取 `traceback` 错误信息并作为新输入塞给大模型继续修改。 |

## Prompt Chaining (提示词链模式)

### 经典要素定义

- **分类**：工作流模式 (Workflow Pattern)
- **意图**：将一个复杂的、多步骤的生成任务，分解为一组串行的、职责单一的提示词执行链，前一步的输出作为后一步的输入。
- **动机**：大模型在单次调用中处理过多业务逻辑或长流程时，容易出现注意力分散、指令违背和幻觉。通过微观解耦，可以显著提升每一步的确定性。
- **适用性**：
  - 任务可明确拆解为前后依赖的线性步骤（如：数据提取 $\rightarrow$ 翻译 $\rightarrow$ 格式化）。
  - 步骤间需要进行中间状态拦截、验证或清洗。
- **结构**：`[输入] -> (LLM 步骤 A) -> [中间输出] -> (数据转换/清洗) -> (LLM 步骤 B) -> [最终输出]`
- **效果**：
  - *优点*：提高复杂指令遵循率；便于工程化调试与单点问题定位。
  - *缺点*：端到端延迟随步骤呈线性叠加；中间步骤出错会产生误差传递。

### 伪代码示例

```python
import json
from typing import Dict, Any

class PromptChainingWorkflow:
    def __init__(self, llm_client):
        self.llm = llm_client

    def step_1_extract_facts(self, raw_text: str) -> str:
        """步骤 1：仅负责从长文中提取核心事实清单"""
        prompt = f"Extract all key facts as a bulleted list from this text: {raw_text}"
        return self.llm.generate(prompt)

    def step_2_classify_sentiment(self, facts: str) -> str:
        """步骤 2：仅负责基于事实，判定结构化的情感极性"""
        prompt = f"Analyze the sentiment of these facts. Return ONLY a JSON object like {{'sentiment': 'positive/negative'}}: {facts}"
        # 确保输出符合 JSON 格式
        response = self.llm.generate(prompt)
        return json.loads(response)

    def run(self, raw_input: str) -> Dict[str, Any]:
        # 串行执行链
        try:
            facts = self.step_1_extract_facts(raw_input)
            # 工程控制：可在此处加入中间数据拦截验证 (Data Guardrail)
            if not facts.strip():
                return {"error": "Failed to extract facts"}
                
            result = self.step_2_classify_sentiment(facts)
            return {"facts": facts, "analysis": result}
        except Exception as e:
            return {"status": "failed", "reason": str(e)}

# 使用示例
# workflow = PromptChainingWorkflow(llm_client)
# final_report = workflow.run("用户投诉长文本...")
```

## Routing / Classifier (路由/分类器模式)

### 经典要素定义

- **分类**：架构/分流模式 (Architecture/Dispatching Pattern)
- **意图**：在工作流入口处通过一个前置分类器识别用户意图，从而动态地将请求分流（路由）到最匹配的特定后端模型、工具或定制化子提示词（Prompt）中。
- **动机**：一揽子提示词（One-size-fits-all）无法兼顾各类差异巨大的输入。将所有工具或上下文塞给单个大模型会导致模型注意力失焦、回答准确率骤降，同时造成高昂的 Token 算力浪费。
- **适用性**：
  - 系统包含多个独立、互斥的业务分支（如 FAQ、代码编写、数据分析）。
  - 需要根据任务复杂度实现模型降级与成本控制（简单任务走小模型，复杂任务走推理大模型）。
- **结构**：`[用户输入] -> (前置分类器: 规则/向量/小LLM) -> [选择路由分支] -> (对应特定子工作流) -> [输出]`
- **效果**：
  - *优点*：隔离复杂性，显著提升特定分支的指令精准度；通过小模型拦截简单请求，最高可降低 70% 的 Token 成本。
  - *缺点*：前置分类带来额外的首字延迟（TTFT）；若分类器判断失误，会导致后续工作流完全不可用（级联错误）。

### 伪代码示例

```python
from typing import Dict, Any

class RoutingWorkflow:
    def __init__(self, classifier_model, fast_llm, reasoning_llm):
        self.router = classifier_model
        self.fast_model = fast_llm          # 经济高效的小模型
        self.reasoning_model = reasoning_llm  # 高成本的深度推理模型

    def _classify_intent(self, user_input: str) -> str:
        """前置路由：利用低延迟小模型或向量相似度判断用户意图类别"""
        prompt = f"Classify the input into one category: 'chitchat', 'math_problem', 'general'. Return only the category name. Input: {user_input}"
        return self.router.generate(prompt).strip().lower()

    def _handle_chitchat(self, user_input: str) -> str:
        return self.fast_model.generate(f"Respond to this casual greeting: {user_input}")

    def _handle_math(self, user_input: str) -> str:
        return self.reasoning_model.generate(f"Solve this math puzzle step-by-step: {user_input}")

    def _handle_general(self, user_input: str) -> str:
        return self.fast_model.generate(f"Answer this general question: {user_input}")

    def route(self, user_input: str) -> str:
        # 执行分类
        intent = self._classify_intent(user_input)
        
        # 动态路由分流
        if intent == "chitchat":
            return self._handle_chitchat(user_input)
        elif intent == "math_problem":
            return self._handle_math(user_input)
        else:
            return self._handle_general(user_input)

# 使用示例
# workflow = RoutingWorkflow(classifier_model, fast_llm, reasoning_llm)
# response = workflow.route("12345 * 6789 等于多少？") # 自动路由至深度推理模型
```

## Parallelization (并行化模式)

### 经典要素定义

- 
- **分类**：工作流模式 (Workflow Pattern)
- **意图**：将多个互不依赖的 LLM 任务进行并行化调用，最后通过代码或聚合大模型将各个子结果合并，以大幅降低多任务执行的总耗时。
- **动机**：对于需要从多角度分析、生成多方案、或执行多个独立子任务的场景，若采用串行（提示词链）处理，端到端延迟会随着任务增加而线性暴增，严重影响用户体验。
- **适用性**：
  - 子任务之间完全解耦，不需要彼此的中间输出作为上下文。
  - 主要分为两种变体：**Sectioning（分块并行）**（如同时进行翻译、法律审核与情感分析）和 **Voting（投票并行）**（如同一个 Prompt 并行生成 3 次取最优解）。
- **结构**：`[用户输入] -> (异步分发) -> [LLM 任务 A / LLM 任务 B / LLM 任务 C] -> (结果聚合器) -> [最终输出]`
- **效果**：
  - *优点*：显著降低整体端到端延迟，总耗时仅取决于执行最慢的那个子任务。
  - *缺点*：在极短时间内产生高并发调用，极易触发服务商的频率限制 (Rate Limit)；Token 消耗量倍增。

### 伪代码示例

```python
import asyncio
from typing import List, Dict, Any

class ParallelizationWorkflow:
    def __init__(self, llm_client):
        self.llm = llm_client

    async def _task_grammar_check(self, text: str) -> str:
        """异步子任务 1：语法与拼写检查"""
        prompt = f"Identify and fix grammar errors in this text, return corrected text only: {text}"
        return await self.llm.generate_async(prompt)

    async def _task_tone_analysis(self, text: str) -> str:
        """异步子任务 2：语气偏向分析"""
        prompt = f"Analyze the tone of this text (e.g., formal, aggressive, polite): {text}"
        return await self.llm.generate_async(prompt)

    async def _task_seo_keywords(self, text: str) -> str:
        """异步子任务 3：提取 SEO 关键词"""
        prompt = f"Extract top 3 SEO keywords from this text: {text}"
        return await self.llm.generate_async(prompt)

    async def run(self, raw_text: str) -> Dict[str, Any]:
        # 并行分发三个独立的 LLM 任务
        tasks = [
            self._task_grammar_check(raw_text),
            self._task_tone_analysis(raw_text),
            self._task_seo_keywords(raw_text)
        ]
        
        # 使用 asyncio.gather 同时并发执行
        results: List[str] = await asyncio.gather(*tasks)
        
        # 聚合器：将并行结果组装为最终结构化报告（此处通过代码直接组装，亦可调用 LLM 聚合）
        summary_report = {
            "corrected_text": results[0],
            "detected_tone": results[1],
            "seo_keywords": results[2]
        }
        return summary_report

# 使用示例
# workflow = ParallelizationWorkflow(llm_client)
# report = asyncio.run(workflow.run("原始待处理长文本..."))
```

## Orchestrator-Workers (中心编排-执行器模式)

### 经典要素定义

- **分类**：团队协作模式 (Team Multi-Agent Pattern)
- **意图**：由一个中心大模型（Orchestrator）负责动态拆解复杂任务、按需分发给多个专属的子执行器（Workers），并在回收执行结果后进行统一审查、补充或汇总。
- **动机**：对于边界模糊、无法在工程开发期硬编码固定步骤的复杂任务（如：根据一句话需求编写一份行业竞品分析报告），传统的线性链或并行化无法应对过程中的动态变化，需要 AI 具备自主规划和结果质检的能力。
- **适用性**：
  - 任务高度复杂，需要涉及多个不同领域的专业工具或子技能。
  - 子任务的数量和执行顺序无法提前预知，必须依赖上一步的结果动态决定下一步。
- **结构**：`[用户输入] -> (Orchestrator 规划与决策) <-> [分发/回收] <-> [Worker 1 / Worker 2 / Worker 3] -> (Orchestrator 质检汇总) -> [最终输出]`
- **效果**：
  - *优点*：具备极强的任务弹性和自适应能力，能够自主解决不可预测的复杂业务流。
  - *缺点*：极度依赖中心模型（如 GPT-4o 或 Claude 3.5 Sonnet）的极高智商，容易陷入“反复无休止规划”的死循环（Planning Loop），导致成本剧增。

### 伪代码示例

```python
from typing import List, Dict, Any

class OrchestratorWorkersWorkflow:
    def __init__(self, orchestrator_llm, worker_llm):
        self.orchestrator = orchestrator_llm
        self.worker = worker_llm

    def _call_worker(self, worker_type: str, sub_task: str) -> str:
        """根据类型调用特定的专家 Worker"""
        prompt = f"You are a specialist in {worker_type}. Execute this sub-task: {sub_task}"
        return self.worker.generate(prompt)

    def execute_task(self, main_goal: str) -> str:
        # 1. Orchestrator 负责拆解总任务
        plan_prompt = f"Break down this main goal into a list of specific sub-tasks with worker types ('search', 'writer'). Goal: {main_goal}"
        # 假设返回结构化的任务列表 [{'type': 'search', 'task': '...'}, {'type': 'writer', 'task': '...'}]
        sub_tasks: List[Dict[str, str]] = self.orchestrator.generate_json(plan_prompt)
        
        worker_results = []
        # 2. 动态分发并执行子任务
        for item in sub_tasks:
            result = self._call_worker(worker_type=item['type'], sub_task=item['task'])
            worker_results.append(result)
            
        # 3. Orchestrator 汇总结聚并进行质量审查
        summary_prompt = f"Review and synthesize these worker results into a comprehensive final report for the goal '{main_goal}'. Results: {worker_results}"
        final_report = self.orchestrator.generate(summary_prompt)
        return final_report

# 使用示例
# manager = OrchestratorWorkersWorkflow(orchestrator_llm, worker_llm)
# report = manager.execute_task("编写一份新能源汽车2026年市场出海分析报告")
```

## Self-Correction / Reflection (自我修正/反思模式)

### 经典要素定义

- **分类**：质量控制模式 (Quality Control Pattern)
- **意图**：构建一个“生成-评估-修正”的闭环，让模型在正式输出前，通过独立的评估环节检查自身初始输出的缺陷（如语法、逻辑、格式错误），并利用错误反馈指导下一次迭代生成。
- **动机**：大模型往往存在“直觉性单向输出”的致命缺陷（即想到哪写到哪），直接生成复杂代码或结构化文本时极易包含低级错误。引入反思机制类似于人类“写稿-校对-修改”的纠错机制。
- **适用性**：
  - 对输出质量有严苛要求（如自动化代码生成、必须严格符合指定 Schema 的 JSON 输出）。
  - 存在明确的评估准则（可以是另一个 Agent 的 Prompt，也可以是确定性的代码验证）。
- **结构**：`[生成器 LLM] -> (初始输出) -> [评估器 LLM/代码] -> {通过? -> 输出} / {未通过? -> 带有错误上下文的 Prompt -> 重新输入生成器 LLM}`
- **效果**：
  - *优点*：显著提升复杂任务的单次出厂成功率，有效抑制幻觉和格式溃散。
  - *缺点*：成倍消耗 Token 资源，若纠错逻辑不够鲁棒，极易在死胡同里陷入死循环。

### 伪代码示例

```python
from typing import Dict, Any

class SelfCorrectionWorkflow:
    def __init__(self, generator_llm, evaluator_llm, max_retries: int = 3):
        self.generator = generator_llm
        self.evaluator = evaluator_llm
        self.max_retries = max_retries

    def run(self, user_request: str) -> str:
        current_output = ""
        feedback = "None"
        
        for attempt in range(self.max_retries):
            # 1. 生成器参考上一次的反馈（若有）进行生成或修正
            gen_prompt = f"Task: {user_request}. Previous Feedback: {feedback}. Generate the response now:"
            current_output = self.generator.generate(gen_prompt)
            
            # 2. 评估器独立对输出进行审查
            eval_prompt = f"Evaluate this output against the task '{user_request}'. Is it correct? Return JSON with {{'is_valid': true/false, 'critique': '...'}}. Output: {current_output}"
            eval_result: Dict[str, Any] = self.evaluator.generate_json(eval_prompt)
            
            # 3. 检查是否通过
            if eval_result.get("is_valid") is True:
                return current_output  # 质检通过，提前终止并返回
                
            # 未通过，记录反馈进入下一轮循环
            feedback = eval_result.get("critique", "Output does not meet requirements.")
            
        # 达到最大重试次数，安全熔断，返回最后一次的尝试（或抛出异常）
        return f"Max retries reached. Best effort output: {current_output}"

# 使用示例
# workflow = SelfCorrectionWorkflow(generator_llm, evaluator_llm)
# safe_json_output = workflow.run("生成一个包含10个字段的复杂用户配置 JSON 字符串")
```

## Tool Execution Layer (工具执行层隔离模式)

### 经典要素定义

- **分类**：安全与控制模式 (Security/Control Pattern)
- **意图**：将大模型的“工具调用决策（Tool Call Decision）”与“工具的实际执行（Tool Execution）”在物理或逻辑上完全剥离开来，放入安全的沙箱或硬编码的代码控制层中执行。
- **动机**：大模型生成的 API 参数或生成的代码存在不确定性，且容易受到“提示词注入攻击（Prompt Injection）”。若直接赋予大模型在底层服务器上写数据库、运行 shell 脚本的权限，会导致系统被恶意操控或引发逻辑灾难。
- **适用性**：
  - 生产环境中允许 AI 智能体调用外部具有副作用的 API（如：扣款、删除、发送邮件）。
  - 需要对 AI 自动生成的代码（如 Python、SQL）进行动态运行和结果抓取的场景。
- **结构**：`[LLM] -> (输出包含参数的 Tool Call JSON) -> [拦截验证层 (安全 ACL / 人工审查)] -> [隔离沙箱环境执行 (如 Docker)] -> (返回清洗后的结果) -> [LLM]`
- **效果**：
  - *优点*：保障主机系统的绝对安全，支持在执行前切入“人工介入（HITL）”审批，提供完美的审计边界。
  - *缺点*：增加了系统工程的开发和运维复杂度，涉及沙箱环境的管理。

## Dynamic Memory Management (动态记忆管理模式)

### 经典要素定义

- **分类**：上下文控制模式 (Context Control Pattern)
- **意图**：将复杂的历史交互数据动态划分为短期缓存（Session）、长期结构化实体（Vector/Graph）以及核心人设（User Profile），根据当前对话语义按需提取并注入上下文窗口，实现长效且经济的记忆管理。
- **动机**：大模型的上下文窗口（Context Window）是有限且昂贵的。如果将几十轮对话完完整整地作为 Prompt 丢给大模型，会导致严重的“迷失在中间（Lost in the Middle）”现象，大幅拉低召回准确率，并造成 Token 费用的指数级暴增。
- **适用性**：
  - 需要超长会话（如长达数月的陪伴式 AI、高频交互的个人助理）。
  - 跨会话（Cross-session）场景，AI 需要在明天的对话中记住用户今天的偏好和特定事实。
- **结构**：`[用户新输入] -> (实体/意图提取) -> [查短期缓存 + 查向量库/图数据库] -> (动态压缩与修剪) -> [组装精简 Prompt] -> (LLM 推理)`
- **效果**：
  - *优点*：打破大模型原生上下文长度限制，保持长期人格与信息的一致性，有效控本。
  - *缺点*：后台需要频繁触发额外的总结（Summarization）和异步写入操作，增加了系统的后台 Token 开销。

### 伪代码示例

```python
from typing import List, Dict, Any

class MockVectorDb:
    def search(self, query: str) -> List[str]: return ["用户在3天前提到过他有一只猫叫喵喵"]
    def upsert(self, text: str): pass

class DynamicMemoryManager:
    def __init__(self, llm_client, vector_db: MockVectorDb):
        self.llm = llm_client
        self.db = vector_db
        self.short_term_buffer = [] # 短期缓存，仅保留最近3轮对话

    def _async_background_extract(self, user_input: str, ai_response: str):
        """异步后台任务：提取核心长期事实并写入长期记忆"""
        extract_prompt = f"Extract permanent user facts (like hobbies, pets) from this chat: User: {user_input}, AI: {ai_response}. Return None if empty."
        fact = self.llm.generate(extract_prompt)
        if fact and "none" not in fact.lower():
            self.db.upsert(fact)

    def chat(self, user_input: str) -> str:
        # 1. 动态召回：根据当前输入从长期记忆库检索相关上下文
        long_term_contexts = self.db.search(user_input)
        
        # 2. 动态组装：将长期记忆、短期缓存和新输入融合
        context_str = "\n".join(long_term_contexts)
        history_str = "\n".join(self.short_term_buffer[-6:]) # 只取近期几轮
        
        final_prompt = f"Long-term memory:\n{context_str}\n\nRecent chat:\n{history_str}\n\nUser: {user_input}\nAI:"
        response = self.llm.generate(final_prompt)
        
        # 3. 记忆更新：更新短期缓存
        self.short_term_buffer.append(f"User: {user_input}")
        self.short_term_buffer.append(f"AI: {response}")
        
        # 4. 异步触发长期记忆沉淀（防止阻塞主流程）
        self._async_background_extract(user_input, response)
        
        return response

# 使用示例

# reply = memory_agent.chat("给我的宠物买点什么零食好？") # 自动唤醒关于“猫叫喵喵”的记忆
```

## Evaluator-Optimizer (评估-优化器循环模式)

### 经典要素定义

- **分类**：生成迭代模式 (Generation Iteration Pattern)
- **意图**：通过一个专属的评估器对生成器的输出进行可量化的客观测试（如编译测试、单元测试或指标打分），并将测试崩溃日志或不达标数据作为负反馈喂给优化器，驱动系统通过多轮循环迭代直至通过全部硬性指标。
- **动机**：反思模式（Reflection）通常依赖于大模型主观的语义评估，而许多技术场景需要严格的客观事实支撑。例如编写代码时，代码是否能跑通、测试用例是否全过，无法靠模型“看一眼”保证，必须依赖真实的测试反馈。
- **适用性**：
  - 自动化软件工程（AI Coding），需要通过编译器检查或通过特定测试用例。
  - 可以通过代码或客观工具定义出清晰、非模糊的成功指标（如：通过率达 100%、文件格式完全合法、计算结果匹配）。
- **结构**：`[优化器 LLM] -> (生成内容) -> [自动化测试/硬编码评测环境] -> {全部通过 -> 输出} / {失败 -> 抓取真实报错/Traceback 丢回优化器 LLM 重新调整}`
- **效果**：
  - *优点*：能突破模型原生能力的上限，产出符合生产级可用标准的、经过验证的高质量技术成果。
  - *缺点*：高度依赖完备的自动化测试沙箱；由于存在真实运行和多轮循环，整体耗时较长。

### 伪代码示例

```python
import subprocess
from typing import Dict, Any

class LocalTestRunner:
    """真实的本地测试环境，用于执行代码并捕获客观报错"""
    def run_tests(self, code: str) -> Dict[str, Any]:
        # 模拟将代码写入临时文件并运行 pytest
        # 实际工程中需在沙箱内运行
        if "def test_sum():" not in code:
            return {"status": "failed", "error": "NameError: test_sum is not defined"}
        if "return a + b" not in code:
            return {"status": "failed", "error": "AssertionError: 1 + 1 != 3"}
        return {"status": "passed", "error": ""}

class EvaluatorOptimizerWorkflow:
    def __init__(self, optimizer_llm, test_runner: LocalTestRunner, max_iterations: int = 4):
        self.optimizer = optimizer_llm
        self.runner = test_runner
        self.max_iter = max_iterations

    def generate_verified_code(self, requirements: str) -> str:
        current_code = ""
        error_logs = "None (Initial Attempt)"
        
        for i in range(self.max_iter):
            # 1. 优化器基于客观错误日志重新调整并生成代码
            prompt = f"Write Python code for: {requirements}. Previous test execution error logs: {error_logs}. Output code only."
            current_code = self.optimizer.generate(prompt)
            
            # 2. 评估器（客观测试运行层）执行并捕获真实反馈
            test_result = self.runner.run_tests(current_code)
            
            # 3. 检查是否通过客观指标
            if test_result["status"] == "passed":
                return current_code # 客观验证通过，安全出厂
                
            # 未通过，抓取真实报错日志进入下一轮循环优化
            error_logs = test_result["error"]
            
        return f"Optimization failed within limits. Last code: {current_code}"
```

## RAG-Router Fusion (知识检索融合模式)

### 经典要素定义

- **分类**：检索增强模式 (Retrieval-Augmented Pattern)
- **意图**：在知识检索的入口处对查询本身的知识跨度和复杂度进行前置评估，动态融合多种级别的检索机制（不检索、向量 RAG、混合检索或多跳图检索），以兼顾企业知识库的响应效率与深度关联性。
- **动机**：简单的知识问答（如“公司几号发工资”）直接回答或使用简单的向量匹配即可，启动复杂的全局检索纯属浪费；而复杂的跨部门关联分析（如“结合近三年财报分析供应链风险”）靠简单的向量相似度召回极易漏掉关键上下文。
- **适用性**：
  - 企业级海量知识库系统，同时面临轻量 FAQ 和跨文档复杂深度关联查询。
  - 需要对大规模高并发检索请求进行服务分级、降低向量数据库并发压力的生产环境。
- **结构**：`[用户查询] -> (检索路由器) -> [无需检索直接答 / 向量检索密集召回 / GraphRAG 跨文档多跳检索] -> (上下文重排/融合) -> [LLM 推理输出]`
- **效果**：
  - *优点*：在高并发、低复杂度的请求中省去重度检索，极大地降低了端到端延迟和服务器开销；对复杂长尾查询提供了极高的信息召回完整度。
  - *缺点*：需要同时构建、维护多套索引体系（如密集向量索引与 Neo4j 图索引），工程复杂度极高。

### 伪代码示例

```python
from typing import List, Dict, Any

class MockMultiIndexStore:
    def vector_search(self, query: str) -> List[str]: return ["匹配到规章制度第3条：10号发工资"]
    def graph_rag_search(self, query: str) -> List[str]: return ["实体A与实体B关系关联", "财报数据链路汇总"]

class RagRouterFusionWorkflow:
    def __init__(self, router_llm, generator_llm, store: MockMultiIndexStore):
        self.router = router_llm
        self.generator = generator_llm
        self.store = store

    def answer_question(self, query: str) -> str:
        # 1. 检索路由器：前置评估查询所需的知识密集度与检索类型
        route_prompt = f"Analyze the query: '{query}'. Choose retrieval type: 'direct' (no data needed), 'dense' (simple factual lookup), 'graph' (complex relationship analysis). Return only the type word."
        strategy = self.router.generate(route_prompt).strip().lower()
        
        contexts = []
        # 2. 动态路由融合检索
        if strategy == "direct":
            # 无需检索，模型内置常识即可作答
            return self.generator.generate(f"Answer directly: {query}")
        elif strategy == "dense":
            # 触发常规高并发、低延迟的向量检索
            contexts = self.store.vector_search(query)
        elif strategy == "graph":
            # 触发深度多跳的 GraphRAG（图检索）挖掘深层关联
            contexts = self.store.graph_rag_search(query)
            
        # 3. 融合召回的上下文生成最终回复
        context_str = "\n".join(contexts)
        final_prompt = f"Answer the query based on retrieved contexts.\nContexts:\n{context_str}\n\nQuery: {query}"
        return self.generator.generate(final_prompt)
```
